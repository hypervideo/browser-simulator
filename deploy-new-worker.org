** Why the deployment path must change
:PROPERTIES:
:CUSTOM_ID: why-the-deployment-path-must-change
:END:
The current =deploy-worker= recipe uploads secrets with =wrangler secret put=
/before/ it deploys the Worker. That is a poor bootstrap path when the Worker no
longer exists. Current Wrangler can upload secrets with the first deployment
through =wrangler deploy --secrets-file=, which removes that ordering problem.
Cloudflare also recommends treating the Wrangler configuration as the source of
truth. [[https://developers.cloudflare.com/workers/wrangler/commands/workers/][Wrangler deploy documentation]]

There is also a credential-boundary problem. The present setup can put the broad
deployment token into the running Worker as =CLOUDFLARE_API_TOKEN=, and the
runtime code accepts it as a fallback. Deployment credentials should remain in
CI or the developer shell. The Worker should only receive the narrow Browser
Rendering token.

** CI secret-management decision and later Infisical migration
:PROPERTIES:
:CUSTOM_ID: ci-secret-management-decision-and-later-infisical-migration
:END:
*** Current decision
CI will use two GitHub =staging= environment secrets for the first deployment:

- =CLOUDFLARE_RW_API_TOKEN=
- =CLOUDFLARE_BROWSER_RENDERING_API_TOKEN=

We attempted to create the dedicated Infisical machine identity
=Github (cloudflare-browser-simulator:staging)=. Infisical rejected the request
because the organization had reached its identity limit. Reusing an existing CI
identity would give this repository every permission held by that identity.
That would break the least-privilege boundary, so we will not reuse one.

This is a CI-only exception. Infisical remains the source for local development
and manual deployment secrets. The GitHub workflow keeps the two tokens in the
=staging= environment and exposes them only to the deployment step. The Worker
receives only the Browser Rendering token. Wrangler receives the deployment
token only while it deploys.

*** Prerequisites for moving CI to Infisical
Complete these checks after the Infisical machine identity limit increases:

1. Confirm that the organization has a free identity slot.
2. Confirm that =hyper-env= still has the two staging secrets at these exact
   paths:

   | Path                                                      | Secret                                   |
   |-----------------------------------------------------------+------------------------------------------|
   | =/infrastructure/cloudflare/cloudflare-browser-simulator= | =CLOUDFLARE_RW_API_TOKEN=                |
   | =/providers/cloudflare-browser-rendering=                 | =CLOUDFLARE_BROWSER_RENDERING_API_TOKEN= |

3. Confirm that neither path imports secrets from another folder. The future CI
   workflow will use =include-imports: false=.
4. Keep the deployment token out of the shared
   =/infrastructure/cloudflare= path.
5. Keep the GitHub environment secrets until an Infisical-backed deployment and
   smoke test both pass.

*** Create the least-privilege machine identity
1. Open =hyper-env= in Infisical and go to =Access Control -> Machine
   Identities=.
2. Create a project-level identity named
   =Github (cloudflare-browser-simulator:staging)=.
3. Set its base project role to =No Access=.
4. Leave =Additional Privileges= empty during creation. The quick =Secret
   Viewing Policies= choice does not show environment or path conditions, so it
   is too broad for this identity.
5. Open the new identity and add one permanent additional privilege named
   =cloudflare-browser-simulator-staging-read=.
6. Add two =Secret Viewing Policies= entries to that privilege. Restrict both to
   the =staging= environment. Restrict one entry to each exact path in the table
   above.
7. Review the effective permissions for the identity. It must be able to describe and
   read secret values at those two paths. It must not be able to create, edit,
   or delete secrets.
8. Verify that the identity has no access to =staging:/infrastructure/cloudflare=
   or any development and production environment.

The identity must have no other project roles or privileges. Infisical combines
permissions from every assigned role, so an extra Viewer or Member role would
expand access for the identity.

*** Configure GitHub OIDC authentication
Infisical creates project identities with Universal Auth by default. Replace it
with OIDC:

1. Remove the Universal Auth configuration for the identity. Do not create a client
   secret.
2. Add the =OIDC Auth= method with these values:

   | Field                     | Value                                                                          |
   |---------------------------+--------------------------------------------------------------------------------|
   | OIDC Discovery URL        | =https://token.actions.githubusercontent.com=                                   |
   | Issuer                    | =https://token.actions.githubusercontent.com=                                   |
   | Subject                   | =repo:hypervideo/cloudflare-browser-simulator:environment:staging=              |
   | Audience                  | =https://github.com/hypervideo=                                                 |
   | CA certificate            | Leave blank                                                                    |
   | Additional claims         | Leave blank unless repository policy requires them                             |
   | Access token TTL          | =3600= seconds                                                                 |
   | Access token maximum TTL  | =3600= seconds                                                                 |
   | Access token maximum uses | =0=. Rely on the short lifetime instead of guessing how many requests the action makes |
   | Trusted IPs               | Leave unrestricted because GitHub-hosted runners have no stable outbound IP     |

3. Save the method and copy the non-secret machine identity ID.
4. Keep the subject exact. Do not replace the repository, environment, or
   audience with a wildcard.

The =staging= job environment is important because GitHub includes it in the
OIDC subject. Infisical verifies the issuer, subject, and audience before it
issues a short-lived access token. [[https://infisical.com/docs/integrations/cicd/githubactions][Infisical GitHub Actions guide]]
